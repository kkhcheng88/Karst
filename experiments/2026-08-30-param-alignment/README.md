# KARST-094 驗收:參數集對齊標記落庫(D-038)

2026-08-30。目的:把 D-038 的「已對齊／示例」由記憶體搬入庫身,而 **正式運行的編號逐位
不變、既有寫入者簽章一個不動**。

**先講清楚兩個數。** `backtest_run` 裡 `origin='formal'` 的是 **13 列**,而**算數的正式
運行是 12 條**——其中 `run-47479e5b36fed94a` 已由 KARST-093 除名,除名是加一列不是刪一列,
所以它的列照舊在庫內。下面逐格核的是那 13 列(除名那條一併核,是 12 條的超集),
講「不變」的口徑亦是 13 列全部不變。

## 為什麼走旁表

落庫兩條路都撞牆(KARST-090 票上已算過):

- 當一格參數值 → 參數集內容變 → 運行編號由參數集內容雜湊而來(KARST-026)→ 13 條全部改號。
- 做成 `param_set` 一條新欄 → 該表的 `content_digest` 變 → 8326 列既有簽章一次過作廢 → `karst verify` 全紅。

主腦裁決:標記是**治理資料**,不是策略身份的一部分,所以不應該進運行編號的雜湊
(假設 A-014,2026-08-30 查證成立)。於是走一張經唯一入口簽章的旁表
`param_set_alignment`,追加式、不可刪、入治理清單。

## 這裡有什麼

| 檔 | 是什麼 |
|---|---|
| `baseline_runs.json` | 動庫**之前**那 13 列正式運行的整列內容(逐格核的對照組) |
| `baseline_signatures.txt` | 動庫之前 51832 列寫入者簽章的 sha256 `9bedb408…` |
| `backfill_094.py` | 補記腳本:正式運行所用的 13 個參數集一律補記「示例」,依據句「D-038:未經用戶對齊」。一切經唯一入口,逐列蓋簽章 |
| `backfill_094.json` | 補記結果逐個參數集落檔,連補記後的三類核對報告 |
| `verify_094.py` | **驗收腳本**:對住真庫逐格核那 13 列正式運行,並把備份庫與現庫的 `gateway_write` 全表逐列比。唯讀 |
| `verify_094.json` | `verify_094.py` 的結果 |
| `verify_090.before-094.json` | 動庫之前 KARST-090 那份驗收報告,留作對照 |

**`baseline_runs.json` 那個 `sha256` 欄不要再引作證據。** 它的計法沒有寫低,接手核實時
試過 50 幾種序列化組合都砌不回同一個值,即是說下一個人一樣重現不到。`verify_094.py`
改為**逐格比**,不靠雜湊——逐格比本來就比雜湊強:雜湊只答「一不一樣」,逐格比答得出
「哪一條、哪一格不一樣」。

## 核出來的結果

1. **那 13 列正式運行逐格不變(含已除名那條;算數的 12 條在內)。** `verify_094.py`
   把 `backtest_run` 全部 13 個欄位逐條逐格與 `baseline_runs.json` 比,對不上的:**0 格**。
2. **既有簽章一個不動。** 備份庫那 51832 列簽章,現庫一列都沒有消失、沒有改過
   (`verify_094.py` 全表逐列比,removed = 0);現庫 51845 列,多出來的 13 列
   **全部**是 `param_set_alignment` 的新簽章。
3. **KARST-090 那份驗收原樣重跑,結論不變。**
   `python experiments/2026-08-30-executor-verify/verify_090.py` → 13 條身份層全部 ✔,
   內容層因子混合那條真的重跑一次引擎,逐日淨值、逐日持倉、逐筆訂單全部 `True`,
   結論「全部逐位相同」;它落的那份 `verify_090.json` 與 094 之前那份**逐字相同**。
4. **verify 三類清白。** 定義:清白(50826 列)、因子批次:清白(997 列)、
   快照:清白(22 列)。對齊標記併入「定義」類,理由見 `karst/gateway/ledger.py`。
5. **庫身版本:程式常數由第 15 版升到第 16 版,而生產庫本身是由第 14 版跳到第 16 版。**
   兩個數不同,不是有人數錯:KARST-091 加 `sweep_batch` 時把程式的 `SCHEMA_VERSION`
   升到 15,但生產庫在 094 之前一直沒有被新程式開過,所以它的 `schema_meta` 仍然停在
   14、連 `sweep_batch` 那張表都未建。094 這次開庫,兩張表(`sweep_batch` 與
   `param_set_alignment`)一次過補建,版本直接由 14 走到 16。DDL 全部
   `CREATE TABLE IF NOT EXISTS`,既有登記一列不動——上面第 1、2 點就是這句話的證據。
   `sweep_batch` 補建後是 0 列,那屬 KARST-091 的帳,不在本票範圍。

## 補記的範圍

**只補正式運行所用的那 13 個參數集。** 掃描格那 8000 幾個是掃描展開出來的取值,
不是拿去做現役設定的候選;補它們只會令這張表被雜訊淹沒,而真正要分辨的那十幾個反而
被埋。依據句逐列同一句是誠實的:那不是逐個參數集判出來的結論,而是 D-038 已經替全部
未對齊的取值講了的那一句。
