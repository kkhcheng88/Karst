## 一、現況(2026-09-23 實測與讀碼)

- `karst/daily.py` 的 `refresh_scope` 逐隻**順序**執行;每隻取價格＋兩個 RSS,再由全部行情證據重建整條日線、再跑 `plan_update`。9/22 十隻證券約 73 秒,約 7 秒一隻。按此推算 200 隻約 25 分鐘,單次 MCP 呼叫必然超時。
- 技術面每日由全部證據檔重算,不是只加新一根。
- 「歷史夠不夠」三套門檻(daily 200 根、出圖 2 根、發布 0.9);證券身份只有一處核對。
- 取源覆蓋表達不到「部分來源成功」,新聞以旁路檔補救。

## 二、生產級目標(驗收時量度,不達標不算完成)

| 項 | 目標 |
|---|---|
| 規模 | 同一名單 200 隻證券可每日刷新 |
| 價格＋技術面增量 | 雲端 200 隻 ≤ 5 分鐘(已有歷史者只取新 K 線,技術面由已存序列加新 K 線更新) |
| 連新聞 | 雲端 200 隻 ≤ 10 分鐘;每個來源有速率上限與退避重試 |
| 單次呼叫 | 每次 MCP 呼叫 ≤ 60 秒返回;長批次在背景分段執行,以 run_id 查進度及續跑 |
| 全量重取 | 已有足夠歷史的證券零次全量重取;缺歷史的補取單獨計數 |
| 失敗 | 一隻失敗不阻其他;失敗明列、可只補跑失敗者 |
| 增量建置 | 按「甚麼更新了」決定重評哪幾層,沿用 `karst/updates.py` 既有路由表(價格 → L4／L5／L6;新聞／研報 → L2／L3／L4／L6;申報 → L2–L6);未受影響的層沿用並保留原評估日期 |

**增量建置(用戶 2026-09-23 更正)**:用戶原話「when 不改任何研究判斷 I think it is not ok. So actaully at first, the system should have increment build mode, given what is updated, then to review what. Like if only price is updated, then only the technical agent will review. And then the investment plan always be updated?」。取代初稿的「平靜只推進價格」。分層如下;**用戶 2026-09-23 以「ok」確認**:計劃數字每日由系統機械更新,LLM 技術分析與計劃重寫只在事件觸發時執行,不是每股每日讀圖:

1. **每股每日機械層**:新 K 線、技術指標與結構、距計劃各價位、現價對公允價值的空間(L4 現價要求)、R&R、入場／失效／目標觸發狀態。每日寫一份「日更快照」掛在研究版本下,計劃的數字每日更新。
2. **事件觸發的 L5／L6 agent**:機械層偵測到觸發狀態改變、關鍵價位或 200 日線被突破／失守、結構事件、R&R 越過門檻或跳空大於數個 ATR 時,技術 agent 重讀圖,計劃 agent 改寫計劃;L1–L4 沿用。
3. **來源觸發的分層重評**:新新聞／研報／申報按路由表重評相應層,再到 L6。
4. 未有正式研究的雷達成員只有機械技術快照,沒有計劃可更新。

新聞覆蓋完整且零候選時才推進新聞窗口,符合「不越過未讀新聞推進窗口」的既有規則。

## 三、工作包與次序

1. **基準量度**:通用基準命令(假客戶端、可注入延遲、成員數參數化)＋雲端十隻逐階段計時。
2. **證券價格序列 module**(候選一):一個入口負責身份核對、口徑、交易時段、歷史門檻與增量接駁;六個呼叫點改用它。
3. **來源覆蓋回報**(候選五):取源結果能表達逐來源成功／失敗／部分,移除新聞特例旁路。
4. **日更規模化**:增量 K 線、已存技術面快照、有界並行與逐來源速率上限、背景分段執行、機械分流。依賴 1–3。
5. **增量分流 module**(候選三):watch → plan → check 的輸入收集與新聞窗口規則集中,可經 interface 測試。
6. **公司證據倉 module**(候選二):研究檔佈局藏在 interface 後;證券身份單一出處;寫入一律原子。
7. **研究收件**(候選四):一次保存只讀一次、驗證不跨 seam 重複。依賴 6。
8. **計算器目錄**(候選六):方法名單單一出處;API adapter 不必 import 整個 service。
9. **增量範圍控制**(KARST-262,用戶 2026-09-23 追問「whether the daily incremental process can really have the scope and update control?」):現況路由只是建議,保存時模型可改任何一層。改為更新任務帶明確範圍;範圍外各層由系統沿用;越界須聲明理由;範圍內每層須有已審證明;記層級變更來源;沿用層過期強制入範圍。依賴 4、5、7。
10. **規模驗收**:獨立測試名單(非生產 daily-monitoring)登記 150–200 隻流動性足夠的美股,雲端實跑兩日,量度第二節各項。

## 四、紀律

- 程式只住 `karst/`,代號與日期由參數傳入,不寫一次性腳本(D-180)。
- 在分支 `daily-scale` 開發;每個工作包全套測試通過才合併;合併 master 即觸發 Zeabur 部署,合併前確認不影響當日排程。
- 研究判斷與已發布版本不因重構改變;既有研究、閱讀站歷史頁逐 bytes 保持;凍結 84 包不動。
- 每張票由 Opus 實作,主 agent 覆核合併。
