# 日更規模化與架構加深——執行計劃 v1(2026-09-23)

> 起因:用戶原話「I would like to make sure we are in production grade. I mean the increment refresh of everyday should be fast and depends on the news and report incremented. As in the whole project is not for monitoring 1 stock, it could be like 100+ or 200 stock to refresh. Maybe mainly just price and technical updates. But still is is not always a full refresh and I want to make sure it will be smooth.」及「And yes, 1 - 6 should be done.」(指 2026-09-23 架構評審六個候選)。

## 一、現況(2026-09-23 實測與讀碼)

- `karst/daily.py` 的 `refresh_scope` 逐隻**順序**執行;每隻取價格＋兩個 RSS,再由全部行情證據重建整條日線、再跑 `plan_update`。9/22 十隻證券約 73 秒,約 7 秒一隻。按此推算 200 隻約 25 分鐘,單次 MCP 呼叫必然超時。
- 技術面每日由全部證據檔重算,不是只加新一根。
- 「歷史夠不夠」三套門檻(daily 200 根、出圖 2 根、發布 0.9);證券身份只有一處核對。
- 取源覆蓋表達不到「部分來源成功」,新聞以旁路檔補救。

## 二、生產級目標(驗收時量度,不達標不算完成)

| 項 | 目標 |
|---|---|
| 規模 | 同一名單 200 隻證券可每日刷新 |
| 價格＋技術面增量 | 雲端 200 隻 ≤ 5 分鐘(已有歷史者只取新 K 線,技術面由已存序列加新 K 線更新) |
| 連新聞 | 雲端 200 隻 ≤ 10 分鐘;每個來源有速率上限與退避重試 |
| 單次呼叫 | 每次 MCP 呼叫 ≤ 60 秒返回;長批次在背景分段執行,以 run_id 查進度及續跑 |
| 全量重取 | 已有足夠歷史的證券零次全量重取;缺歷史的補取單獨計數 |
| 失敗 | 一隻失敗不阻其他;失敗明列、可只補跑失敗者 |
| 分流 | 無新來源且無條件觸發者機械記錄「平靜」,只推進價格;有新新聞／研報或觸發條件者進 agent 隊列 |

**假設(未經用戶逐項確認,如錯請更正)**:機械「平靜」記錄不改研究判斷,只記錄「無新來源、無條件觸發」;新聞覆蓋完整且零候選時才推進新聞窗口,符合「不越過未讀新聞推進窗口」的既有規則。

## 三、工作包與次序

1. **基準量度**:通用基準命令(假客戶端、可注入延遲、成員數參數化)＋雲端十隻逐階段計時。
2. **證券價格序列 module**(候選一):一個入口負責身份核對、口徑、交易時段、歷史門檻與增量接駁;六個呼叫點改用它。
3. **來源覆蓋回報**(候選五):取源結果能表達逐來源成功／失敗／部分,移除新聞特例旁路。
4. **日更規模化**:增量 K 線、已存技術面快照、有界並行與逐來源速率上限、背景分段執行、機械分流。依賴 1–3。
5. **增量分流 module**(候選三):watch → plan → check 的輸入收集與新聞窗口規則集中,可經 interface 測試。
6. **公司證據倉 module**(候選二):研究檔佈局藏在 interface 後;證券身份單一出處;寫入一律原子。
7. **研究收件**(候選四):一次保存只讀一次、驗證不跨 seam 重複。依賴 6。
8. **計算器目錄**(候選六):方法名單單一出處;API adapter 不必 import 整個 service。
9. **規模驗收**:獨立測試名單(非生產 daily-monitoring)登記 150–200 隻流動性足夠的美股,雲端實跑兩日,量度第二節各項。

## 四、紀律

- 程式只住 `karst/`,代號與日期由參數傳入,不寫一次性腳本(D-180)。
- 在分支 `daily-scale` 開發;每個工作包全套測試通過才合併;合併 master 即觸發 Zeabur 部署,合併前確認不影響當日排程。
- 研究判斷與已發布版本不因重構改變;既有研究、閱讀站歷史頁逐 bytes 保持;凍結 84 包不動。
- 每張票由 Opus 實作,主 agent 覆核合併。
