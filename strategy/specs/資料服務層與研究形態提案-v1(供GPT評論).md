# 資料服務層與研究形態提案 v1(2026-09-16;供 GPT 評論)

> 起因:AXTI 首跑與修訂版之後,用戶、GPT 與本地主 agent 三方在 2026-09-16 的討論收斂出一個方向——**資料層純機械、放上網;研究由強模型帶網頁搜尋自由進行;工程欄位與計算由程式產生;隔離落在工具層。** 本文把討論寫成可評論的提案,落地前請 GPT 逐節評論;所有「同意」「不同意」以用戶裁決為準。本文是提案,不是已實作。

## 零、一句話

保留 Karst 的投研方法(六層問題、證據出處、估值推導、更新規則)與資料記憶;把資料取得與計算做成任何模型都能呼叫的線上服務;讓一個主研究模型對完整投資建議負責,反方深度跟隨爭議重要性;Claude Code 退回開發工具位。**成功標準是用戶更快拿到完整、可行動、會隨新證據更新的判斷,不是治理規則的數量。**

## 一、責任分配(GPT 2026-09-16 提出,本地同意)

| 部分 | 負責 |
|---|---|
| 強模型(主研究) | 理解生意、找資料(含網頁)、提出假設、辨認預期差、選估值方法、形成完整投資建議、講明相對上次改了什麼 |
| 工作流 | 派工、傳遞結果、按問題補查、必要時退回重評(DAG、條件分支、有限次重評) |
| 程式 | 保存來源與時間、計算估值 / TA / R&R、檢查單位與期間、產生 ID / 雜湊 / 時間 / 版本、出頁 |
| 第二模型(反方 / 覆核) | 只覆核足以改變決策的重要爭議;可換供應商;可要求它找新證據;票數不是結論依據 |

兩點本地補充:**(1)** 主研究角色從頭到尾持有論點——首跑的結構問題正是五份 JSON 各自完整、「所以現在怎樣看」由綜合層在最後拼出來。**(2)** 反方與正方犯同類錯(首跑兩者都把年底季度速度乘四當全年)說明多角色不抵消共同前提錯;算式類錯誤交程式計算器擋,不交更多角色。

## 二、資料服務層:哪些今天就能純機械上線

| 來源 / 功能 | 上線 | 備註 |
|---|---|---|
| EDGAR(年報、季報、8-K 含附件、招股書、索引)| 可 | 公開 HTTP;要聯絡用 User-Agent;**取數器要補抓 8-K 的 EX-10 合約附件**(首跑只抓 EX-99.1) |
| DefeatBeta(逐字稿、三表、日曆、公司資料)| 可 | 公開資料集;`defeatbeta-api` 須 0.0.61 起 |
| Longbridge(報價、日 / 週 / 月線、共識、EPS 預測序列、評級 / 目標價歷史、沽空、持股、申報清單、新聞、宏觀)| 可 | 雲端 API,帶用戶 token;**token 必須只有行情權限,無交易權限**(待核) |
| 日線 | 可 | **單隻股票由 Longbridge 隨取,yfinance 退場**(用戶 2026-09-16);橫向掃描用的多股序列由程式定時抓存服務端 |
| 登記器、取證包、估值 / R&R 計算器、出頁 | 可 | 已是純程式 |
| 富途 | 第一版不接 | 要本機閘道;資料與 Longbridge 大部分重疊;需要時再由閘道連回用戶機器(用戶 2026-09-16) |

**服務暴露的工具(第一版六至八個):** 取申報 / 取逐字稿 / 取價格 / 取共識與評級 / 抓網址並登記快照 / 搜尋與讀取已保存原文 / 算估值與 R&R / 登記研究產物。**帳戶、持倉、下單類工具在程式裡不存在**——隔離不靠提示詞。

**部署:** 服務由第一天部署 Zeabur(ChatGPT 的 MCP 連接器要求 HTTPS 遠端端點;在用戶機器開隧道是安全負擔)。儲存先用掛載盤上的 SQLite(0.2 契約的表現成),兩邊要同時查詢時再換 Postgres。GitHub 只放程式與規格;研究產物走服務資料庫,不走 PR。

## 三、模型呼叫層:改走 API,Claude Code 退回開發工具

首跑與修訂版的模型呼叫走 Claude Code 的派工工具,結果是:harness 不限制角色讀哪個路徑(隔離只靠指令)、角色沒有時鐘(六個猜的時間戳)、成本只有 harness 累計數(1.94M / 修訂版約 1.75M,無法拆 input / cached / output)。三件事同一個修法:**服務直接呼叫模型 API,只掛允許清單內的工具**;覆核任務亦由服務呼叫(可換供應商),不經 Claude Code。Claude Code 只維護程式與 GitHub 協作。GPT 原提案中「本機服務呼叫 `claude -p` 做覆核」一格,本地不同意——那要放開 Claude Code 權限無人值守運行,且依賴用戶電腦在線。

## 四、儲存原則(用戶 2026-09-16 挑戰後修訂)

用戶原話要旨:存供應商歷史快照若只為證明當年對錯,沒有價值;關鍵永遠是當前判斷的資訊係數。本地接受一半、保留一半:

1. **存自己的判斷**(評級、內在價值、隱含要求、計劃)——這是算資訊係數的分子,沒有它就無法評方法。
2. **供應商快照只在兩條同時成立時存**:(a) 該資料的時間變化本身進入今天的判斷(例:共識六星期內由 1.3 升到 1.58,是 L4 的現時訊號);(b) 供應商不保留歷史。Longbridge 有 EPS 序列與評級 / 目標價月度歷史,不存;富途共識、沽空、機構持股供應商只給當前值,存(體積小)。
3. **價格 / 宏觀序列不存**,隨取;研究紀錄只寫下「決策時用了哪個數、何時取得」。
4. **序列只為橫向計算才存**(板塊對板塊、幾百隻相對強弱、掃描),由程式定時抓,住服務端。
5. **一手證據快照必存**(申報、逐字稿、協議、分析員報告、用戶筆記)——這不是為可追查,是因為結論引用它的段落。
6. **可追查性不是存的理由。**

## 五、圖:四張表,隨第二隻股票長出來,不先畫全圖

分類沿用六層(市場 / 宏觀、產業 / 價值鏈、公司、預期、價格),不另發明。圖 = 節點之間的邊,每條邊掛來源證據與日期。**現況:未建**——只有證據登記、片段內相位欄、產業層文字裡的關係;增量重評仍靠人手路由。第一版四張表:節點、關係(帶證據)、假設(帶節點;模型寫假設時標它靠哪幾個節點,是唯一要模型配合的事)、來源訂閱(來源 → 節點)。程式判「有沒有新東西」看語義欄位指紋,不看取得時間;變了的證據掛哪個節點 → 哪些假設 → 哪些層,依《補查與增量重評路由 v1》往下游傳。

## 六、來源分級(網頁開放後必須有)

一手來源(申報、逐字稿、公司公告、監管文件、協議原文)可直接支撐結論與數字;二手來源(新聞、研報轉述、SEO 文章、付費牆摘要)只能引出問題,不能單獨支撐數字。模型引用網頁時必須經「抓取並登記」工具取快照,結論引用登記編號而非網址。

## 七、第二隻股票:三形態同日對照

同一標的、同一日、同一資料服務,三種形態各跑一次:(A) 現行六角色 Claude;(B) 單一 Claude 主角色開網頁 + 一次針對性反方;(C) GPT 主研究(ChatGPT 介面,手動,經 MCP 連接器用服務)+ 一次針對性 Claude 覆核。比:由開跑到可行動判斷的時間、成本(API 帳單拆分)、事後核出的錯漏數、遺漏的重要問題。**若 B 或 C 沒有明顯更快、更便宜且沒有更多錯漏,就是我們的假設錯了。** 六角色是否保留由此定,不由架構信念定。
