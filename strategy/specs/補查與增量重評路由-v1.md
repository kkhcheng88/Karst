# 補查與增量重評路由 v1

2026-09-16；承接 D-183、KARST-240 步二與 KARST-242 步三。

**本次是設計與首次運行覆核，不代表路由、跨 packet 沿用或新發布閘門已實作。** 四份資料契約維持 0.2.0；不改寫既有 AXTI 發布、片段或 84 宗凍結資料。進度以 [四類注地圖](../四類注地圖.md) 為準。本文細化 [交付設計 §六](獨立投研工作台設計與交付計劃-v1.md) 的既有增量原則，是實作路由的規則正本；角色格式仍以 [agents README](../../karst/agents/README.md) 及 schema 為準。

## 一、裁定與目前邊界

**新 packet 不等於六個角色全部重跑；新資料、被推翻的假設或方法變動，才決定哪些判斷失效。失效從受影響層傳到依賴它的下游。**

分清三件事：來源版本更新、分析判斷更新、發布畫面更新。例如價格變了，折讓與交易計劃要更新，但不表示公司收入假設跟着變；只登記補查請求，則不表示模型讀過新證據。

現有 `assemble` 要求片段與 packet 身份一致、上游完整 JSON 雜湊一致，並檢查評估時間。它尚未提供跨 packet 沿用協議。**禁止把舊片段的 packet_id、assessed_at、input_hashes 批次改成新值，當作完成重評。** 雜湊證明檔案一致，不能證明模型看過該版本。既有首次運行如有這類轉換，保留原紀錄並揭示其限制；本輪不追補成不存在的模型呼叫。

第二家公司首次分析走現有完整流程，本來就沒有跨股沿用問題。步二先固定每輪輸入、補查落地與發布一致性；步三才交付自動沿用、SQLite 依賴索引及路由。不要因等待步三而停止第二家公司。

## 二、補查不是一張無限等待清單

每項請求要有欲解決的問題、受影響層、若缺失會改變什麼、來源範圍與完成條件。取證角色可合併同一文件的下載，但保留各請求及各自解決狀態；同一份 10-Q 不能由六個角色各抓一次。

| 類別 | 處置 | 何時重評 |
|---|---|---|
| 截至現在可能已公開、只是包內未收 | 先按資料來源正本查原接口及替代來源；例如缺少的歷史日線、已申報增發或供應協議 | 新證據登記並形成新快照後，按第三節路由 |
| 原文已在包內，但口徑／推導有爭議 | 回讀上下文、表格與對照來源；屬分析修訂，不一定需要新 packet | 原判斷若有誤，退回其擁有者及下游；不得一律推到下一季 |
| 未來事件才會產生的資料 | 記驗證事件、預期窗口與訂閱；不反覆向同一接口空抓 | 正式披露或驗證期限到達時 |
| 公開材料仍未回答，或來源取數失敗 | 分別記未披露／歧義與技術失敗；列替代查法、影響及重試條件 | 新材料、成功重試或覆核期限到達時 |

請求的待辦、重試與費用記在 runner 的持久執行紀錄；最終 packet 保留契約要求的請求／解決紀錄。研究片段只能列符合現行契約的自己所屬待補請求，不轉抄別層請求冒充自己的新發現。

有未解問題不自動等於全股不可研究。只阻塞依賴該問題的結論或計劃；能成立的條件情境仍應交付。若決定等待，要指出具體待什麼及今天能完成的補查，而非把全部 20 項等同為入場必要條件。

## 三、路由表

L1 市場宏觀、L2 產業價值鏈、L3 公司基本面、L4 估值與預期、L5 技術、L6 綜合。表內是判斷依賴，不代表新增角色；L1/L2 仍由 industry 擁有。

| 事件 | 必須處理 | 可以沿用的部分／限制 |
|---|---|---|
| 相同來源內容、口徑與公開時間未變，只重抓 | 追加取得觀測；更新抓取成功／失敗狀態 | 不重跑研究。只有新鮮度警示等使用者可見狀態改變時才需要新視圖／發布 |
| 只增補查請求或診斷紀錄 | 更新待辦、覆蓋及可執行性；若改變判斷，交相關層及 L6 | 不假設產生新的經營證據。新 packet 的沿用仍須第四節協議 |
| 一般價格／成交量更新、缺失日線補回 | 程式重算 L5；重算 L4 折讓、現價隱含要求及剩餘回報；L6 更新條件計劃、R&R | L1–L3、未失效的經營／估值假設可沿用。原估值日、原目標日不自動延後；若需滾動估值日，另記時間推移的重估 |
| 突破、失效線觸發或異常價格／量能 | 上述計算加事件補查；L5／L6 判斷條件是否觸發；新增事實再按相應列路由 | 未找到原因就記未知，不能編造新聞或基本面變化；重要行動轉變須覆核交易反證 |
| 新業績、逐字稿、指引或重大申報 | L3 → L4 → 反方覆核 → L6；檢查 L2 暴露及 L5 事件反應 | 只重讀新增材料與必要比較原文，不把未變的全部歷史文件再讀一遍 |
| 增發、債務、資產處置、併購或重大供應協議 | L3 核口徑、現金／債務／股數及經濟權益 → L4 每股價值與情境 → 反方 → L6；必要時 L2 | 不是「只更新新聞」。即使收入預測不變，每股價值也可能失效 |
| 產業／客戶／供應商報告 | L2 更新主張與關係；依不同公司暴露進 L3 → L4 → 反方 → L6 | 以訂閱加依賴查受影響公司，不能只找原來引用此報告的股票；不把產業結論同幅套給每家公司 |
| 宏觀、政策或利率更新 | L1／L2 確認傳導；只觸及相關收入、成本、風險溢價或融資假設及其下游 | 相同新聞不代表所有股票要重做。未知新關係列待查，不當無影響 |
| 來源更正、撤回、時間／期間／單位修正 | 引用該版本或數值的層與下游失效；保留舊發布及原引用 | 原 bytes 相同但財年／口徑修正也可能是重大更新 |
| 原證據未變，但反方／人工找到分析錯誤 | 退回判斷擁有者；如 L3 口徑錯，重做 L3 → L4 → 反方 → L6 | 不需等待新文件。L6 接受反證不能只改評級而留下已否決的 L4 目標 |
| 驗證事件、資料期限或論點期限到達 | 檢查預期事件是否發生、缺席是否有意義，覆核必要假設 | 無新文件也可能需要重評。不能無限沿用老報告 |
| 方法、提示詞或研究委託改動 | 記變更範圍並失效受影響角色及下游；不明範圍則擴大覆核 | 舊發布保留舊方法；不事後改績效分母或重啟目標期限 |

**計算更新與模型重評分開。** 價格日先由程式計算；文字仍有效就保留。有交易條件改變或數值與敘述不符，再給相關角色一個有界修訂任務。目前 L4 片段把估值假設與價格解讀放在一起，實作尚未拆出安全的衍生更新前，讓 L4 做局部覆核；不要直接字串替換 L4 的自然語言。

事件重要性須由版本化規則及論點的失效條件判斷。未確認的新文件不得只因「未被舊卡引用」就跳過；先做有記錄的相關性分流，拿不準則升級覆核。對非重大分類定期抽查，防止漏報。

## 四、何時可以沿用：要有證明，不是改身份

跨 packet 沿用的前提是：實體／證券、引用版本、所需上游判斷、方法與委託仍適用；新增或更正證據不影響該判斷；資料與驗證期限未失效。檢查所有三條路徑：原依賴、訂閱找到的新來源、時間到期。光比舊引用 hash 不足夠。

實作採版本化的 runner 執行清單記以下資料，先與四份 0.2 契約分開，不偷加 schema 未定義欄位：

| 紀錄 | 要回答的問題 |
|---|---|
| 模式 fresh／reused／recomputed | 本次是模型新判斷、沿用舊判斷，還是程式重算？不得混寫 |
| 原片段 hash、原 packet、原 run／publication | 沿用哪一份不可變結果？ |
| 派工時 input hash、實際交付的證據與上游 hash | 模型本來拿到什麼？派工前固定，不能收件後改成最新版本 |
| 原 assessed_at、call started/completed_at、landed_at、revalidated_at | 何時真正評估、何時收件、何時檢查沿用？沿用不刷新原評估時間 |
| 證據／假設依賴及語義輸入 digest | 哪些值與判斷不能變？哪些僅是請求狀態或執行時間？ |
| 方法、提示詞、委託、計算器及路由規則版本 | 同一證據是否仍按同一方法解讀？ |
| 失效／沿用原因、審核結果及新目標 packet | 為何允許沿用？遇未知就待覆核，不預設安全 |

完整檔案 hash 永遠保留。未來用於避免無效下游重跑的「語義 digest」，必須由明確且版本化的欄位投影產生，涵蓋判斷、引用、數值、口徑及缺口；不能用模型一句「大致沒變」取代，也不能把關鍵欄位當 metadata 排除。

新 packet 如需兼容片段，可生成**獨立的沿用投影**，指回原始片段及審核紀錄；原始模型輸出封存不動。這需要 `assemble` 顯式支援與驗證，包含例外允許原 assessed_at 早於新 packet；沒有沿用證明仍走原時間閘門。不得直接取消全域時間檢查，或只在旁邊放一份無人核驗的 JSON 就算支援。

## 五、反方、退回與發布一致性

反方仍是兩步：先盲讀證據形成 `counter_initial`，再讀各層覆核；不讀綜合。

- **只有上游分析修訂，原始重要證據未變**：保留原封存初判，反方第二步看修訂片段，再交 L6。不可把保留初判說成新的獨立模型呼叫。
- **出現足以改變投資論點的新證據**：用新證據先產新的獨立初判，再讀新各層覆核。舊初判保留為前版，不先灌給新初判造成錨定。
- **單純價格重算**：可保留經營反證；重要入場／退出或 R&R 轉變時覆核交易反證。不是每次報價都重跑兩輪反方。

反方的錯誤與正方一樣要核查。被接受的重大挑戰必須指向具體擁有者和欄位：要求修訂、補證據、保留有條件情境或撤回。L6 是裁決者，不能無痕改寫別層；擁有者修正後，下游依新內容覆核。

發布前至少對齊：評級／執行條件、已採納的經營情境、當日價值、期限目標、現價時點、技術資料截止及 R&R。`plan.target_price = null` **本身不代表** L4 的情境目標無效：可能只是沒有選定一個交易目標。但若 L6 明言否決 L4 目標的依據，首頁不能仍把該數字當採納的目標。

0.2 已允許 `valuation.target_prices = []`。針對目標撤回，可由 L4 修订並清空，寫明原因，再由反方／L6確認；若當日 DCF 也受影響，要重估條件情境或用既有 unavailable／gap_reason 表達，不能只把目標隱藏而留下失效的內在價值。未採納的候選仍留原始片段，不能作首頁 KPI 或投入 R&R。如另設情境附錄，需明示未採納及其原因。

數值計算程式守算式、單位、期間及輸入；接受／駁回挑戰的語義決定須由研究覆核。實作可在 runner 加具體決定清單及發布閘門，不宣稱 JSON schema 能自動讀懂兩段論述是否矛盾。

有限補查／修訂輪數及預算由執行配置明記。耗盡時交付一致的受約束結論，不發布互相否決的兩套數字，也不因尚有爭議而必然把評級改成中性。

## 六、步二現在怎樣落地

1. **固定一輪輸入**：取證、登記、選定 as_of 並建立 packet；生成角色 task 時封存實際 input 與上游 hash。as_of 不晚於真實建包時間，不能把 created_at 人工挪向未來；日時精度照契約保留。
2. **land 是驗收，不是補寫閱讀歷史**：保存模型原始 output；runner 記自己的開始／完成／收件時間。可把模型猜的時間替換為有紀錄的真實完成時間，保留原值及轉換原因；檔案 mtime 只可作有揭示的舊 run 補救，複製會改變 mtime。身份或輸入 hash 不符要退回查明，不能一律重蓋。
3. **補查先入執行待辦**：呼叫中新增請求先存 requests／runner 清單，避免每個請求都令全組片段換 packet。新證據由取證角色落地，與新請求狀態一起在明確輪次邊界建立新 packet。
4. **尚未實作沿用的安全過渡**：如果仍用現有嚴格 assembler，最終新 packet 的片段必須由真正匹配該 packet 的任務產出；必要時六角色各做有界覆核並記為新呼叫，不把只改 metadata 當覆核。這是暫時成本，不是步三日常全重跑規則。補查歷史不得為省這輪而遺失或假稱已解決。
5. **先修 AXTI 一致性並跑第二股**：與自動路由開發分開。第二股仍以參數化核心完整運行；修正 land／補查通道及必要發佈檢查後，不需等 SQLite。

新發布保留 previous_packet／previous_publication 關係、原期限及逐項變更原因。相同事件與輸入重試不重複發布；發布中發現相關來源更新，重評受影響層或明列這是較舊快照及待更新項，不能冒充最新。

研究隔離還需本地驗證：只列 Read／Glob／Grep／Write 可限制工具種類，**不能單憑此證明這些工具讀不到 task 目錄之外的檔案**。runner 須用實際路徑允許清單或 sandbox，拒絕外部路徑及帳戶工具，且不繼承開發上下文。用合成禁讀檔驗不能取用；不用真實帳戶資料作測試。重開 session 載入 agent 定義不是完整驗收。

## 八、驗收與分工

GPT 維護通用核心、契約兼容及本規則；本地負責接口、真實模型／工具隔離、實際資料及整合驗收。程式仍走分支與 PR；所有入口參數化，不建股票專屬腳本。
