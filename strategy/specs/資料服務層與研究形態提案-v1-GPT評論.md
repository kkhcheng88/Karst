已讀原提案、資料來源正本、投資委託／決策模型、增量路由 v1、AXTI 修訂紀錄，以及目前發布器與 0.2 契約。AXTI 修訂版已發布，不再列作下一輪開工前置。

## 二、研究自由：放寬來源限制，同時保留可理解的依據

§六把所有二手來源降為「只能引出問題」，會削弱最需要的產業研究。分析員盈利預測、渠道調查、獨立採訪與產業估算，往往正是預期差的材料。應問「這個來源能支持哪一句話」，而非一律按一手／二手准入：

- 原始申報可支持已披露收入；管理層逐字稿可支持「管理層作出某指引」，不保證指引會實現。
- 分析員原報告可支持「該分析員估計市場規模或盈利為多少」；引用時保留作者、日期、定義與方法，不轉寫為公司已實現事實。
- 可靠新聞的原創採訪或調查可支持其報道內容。轉述、付費牆摘要或搜尋片段，只支持實際可見且可核的部分；重大爭議再找交叉證據。

建議把原文改成：

> 研究可使用申報、逐字稿、公司文件、新聞、分析員報告、產業研究與網頁資料。對影響結論的主張標明其屬性：已披露事實、他人預測、報道或本系統推論。引用登記實際讀到的內容與來源；有歧義時按重要性補查。

完整快照成功時照存；失敗時可保存模型實際看見的摘錄、網址、取得時間及覆蓋限制。不假稱讀過全文，也不因抓取器失敗就把已取得的有用資料全部作廢。原生瀏覽工具看見的版本，與服務稍後重新抓到的版本可能不同，應分開記。URL 仍供人點回原文，evidence_id 供程式連接，兩者並用。

另修正 §一的例子：`130 × 4 = 520` 算術沒有錯；錯的是把退出季度速度當成全年收入。模型先判明產品範圍、期間及爬坡假設，程式才計算。不要把「用計算器」寫成已解決共同前提錯誤。

## 三、儲存：保留研究需要的記憶，不累積整套供應商歷史

建議 §四及資料來源 §四用同一張表取代目前互相衝突的條文：

| 資料 | 留什麼 |
|---|---|
| 自己的研究 | 論點、假設、情境、價值、目標期限、計劃、最強反證、與上一版的差異。 |
| 研究引用的文件 | 申報、逐字稿、合約、分析員報告、用戶研究等原文或實際可見摘錄；區分作者觀點與本系統判斷。 |
| 決策使用的供應商數字 | 保存被採用的數值及必要語境：所述期間、單位／幣別、口徑、來源與取得時間。包括計算所用假設和輸出，便於下次解釋改了什麼。 |
| 完整供應商序列 | 按需取用，可在同次研究內快取；不因研究讀過，就永久保存全部 OHLC、共識、沽空或宏觀序列。 |
| 橫向掃描所需序列 | 按實際計算範圍保存，獨立於單股研究；不順便擴成所有來源的每日倉庫。 |

因此「與上次相比」明確指**與上次研究採用的資料及假設相比**。沒有持續保存或供應商可回取的序列，就不能聲稱知道兩次研究之間每次共識修訂；這是功能取捨，不是要求重建歷史庫。

取數失敗可展示上一版研究及其日期，但不能把上一版指標配上今天價格冒充新算結果。成功回傳也須足以支撐當前計算：例如 200 日均線需要足量、口徑一致的日線，不能只以 HTTP 成功判可用。

手動研究可以按需取數；若要主動監察突破、業績或新聞，就仍需要定時檢查來源。**定時檢查與永久保存每日完整回傳是兩件事。** 是否啟動監察跟隨產品階段，不作第二股研究的前置。

目前程式有一項實際落差：`karst/publish.py` 複製所有登記證據檔，並保存完整 `research.json`；0.2 的 `technical.views` 包含日／週／月價格陣列。因此需要把臨時計算資料與長期研究產物分開，明確決定發布保存哪些欄位及原文。先列出必要的契約／封存兼容調整，既有發布保留原樣；不要宣稱只改部署就已符合新儲存規則。

「判斷是資訊係數的分子」建議改成「判斷紀錄支援後續檢視」。資訊係數通常是預測訊號與後續實現結果的相關性，不是一個評級當分子的比率。這不需要現在新增績效研究工程。

## 四、服務與模型：接受 API，保持入口共用

服務端覆核用模型 API 合理：不用依賴用戶電腦在線，容易記錄各次呼叫用量並配置工具。但 API 本身不會自動產生正確時間或控制本地資料；由服務時鐘寫工程欄位、由工具執行層選擇可提供的資料。

`claude -p` 並非必須開放所有權限才能無人值守；官方支援非互動、工具配置與結構化輸出。因此選 API 的理由應是部署及維護方式，而非 CLI 技術上做不到。[Claude Code 官方文件](https://code.claude.com/docs/en/headless)

保留兩種入口接同一套核心：

- **互動研究：**用戶在 ChatGPT 與 GPT 研究，使用原生網頁搜尋及 Karst 資料／計算工具；重要爭議交服務端 Claude 覆核。
- **自動研究：**服務端主模型使用同一資料與計算函式，具備自己的搜尋能力；依需要交覆核。先用直接流程，不預設必須引入 LangGraph。

ChatGPT 的遠端 MCP 連接仍需實際設定及驗證，不能把 GitHub 可讀寫當作資料服務已接通。[OpenAI 官方文件](https://developers.openai.com/api/docs/guides/developer-mode)

Zeabur 可以採用；HTTPS 遠端服務不指定必須哪家雲。SQLite 在單一服務實例加持久磁碟的起步形態合理，**兩個模型同時讀取不是換 PostgreSQL 的理由**。多實例部署、寫入負載或代管需求才是實際評估點；WAL 支援讀寫並行，但共享記憶體機制要求同一主機。[SQLite 官方說明](https://www.sqlite.org/wal.html)

另須更正「0.2 契約的表現成」：現有是 JSON Schema 與檔案發布器，不是現成 SQL 表。可先延用檔案物件，按查詢需要加小索引；不必為上線而先把所有內容遷進資料庫。GitHub 保留程式與規格，部署服務持有研究檔案及索引即可。

Longbridge 的 OpenAPI／SDK 和 MCP 不應寫成同一份功能保證。官方 MCP 已有雲端端點，但工具及回傳依地區、帳戶和授權範圍而異；價格歷史也可能少於請求數量。以實際使用端點列一張小能力表，確認所需欄位及日期範圍，不重新包裝所有券商功能。私有憑證留在服務端。[Longbridge MCP 官方文件](https://open.longbridge.com/docs/mcp)

工具清單應補齊下列能力，可合併入口，毋須拘泥六至八個工具：

| 能力 | 為何需要 |
|---|---|
| 財務三表、分部與公司資料 | 不能只暴露文件、價格及共識，卻沒有機械財務取數。 |
| 公司新聞、業績／事件日曆、網頁搜尋 | 抓 URL 不等於能發現 URL；自動主模型也要有搜尋入口。 |
| 接收報告／研究筆記及可見網頁摘錄 | 延續 inbox 的使用方式，支持付費報告或抓取受限的內容。 |
| TA 計算與資料覆蓋資訊 | 均線、關鍵價位、日週月及 R&R；資料不足需返回具體缺口。 |
| 讀取現有股票／產業研究及本輪差異 | 模型才能在已有認知上更新，而非每次重頭讀。 |
| 提交覆核、查狀態、讀結果 | 較長的模型任務用 job_id 回來取結果，避免依賴一個長連線。 |
| 保存研究及發布股票頁 | 研究完成後立即成為可閱讀產品；沿用現有 renderer。 |

## 五、圖：模型交代依賴，程式管理更新

四類表可作概念起點，但單有「假設依賴節點」尚未閉合路由。要能找到：

> 來源／關係版本 → 假設版本 → 哪家公司、哪一層、哪一版研究採用了它。

後一段可先放研究 JSON，再由索引提取，不為湊表而加表。模型負責說明採用的假設、相關節點及暴露機制；程式檢查編號、版本並查下游。引用只說「讀了哪份材料」，不能反推出「結論依賴其中哪一句」。

欄位指紋判的是輸入有無變化，不能自行判定經濟意義已改變。產業報告更新先找受影響候選，再依各家公司暴露判斷；來源訂閱補發現過去未被引用的新資料。另保留驗證期限到達觸發，沒有新文件也可能需要更新。這些沿用既有路由 v1，不重新發明規則。

首版先證明一個價格更新可局部處理、一個共享產業假設可找到相關公司；完整圖及全自動傳播不阻塞第二股頁面。

## 六、第二股與比較：先交付，再決定是否值得多跑

我選 **INTU**，TTD 為備選。INTU 適合檢查主模型能否分清：AI 對工作流程價值、獲客、分發及定價的不同影響，以及公司自身採用 AI 對成本和產品的作用，再把論點連回分部增長、留存、利潤與估值。這是測試設計判斷，不預設 AI 威脅或利好成立。其業務跨 QuickBooks、TurboTax、Credit Karma、Mailchimp 等，提供拆分分析的條件。[Intuit 公司介紹](https://www.intuit.com/company/)

正式研究使用新上下文，不帶本段開發對話中的個人持倉經歷。標的仍由參數指定，不建 INTU 專用程式。

先跑 C，交出 GPT 主研究加一次針對性 Claude 覆核的完整股票頁。若需比較，B 用相同起始資料與截止時間再跑；A 六角色留作有需要的對照，不要求三套齊備才讓用戶拿到結果。

比較要分清目的：

- A 對 B 可檢查角色拆分成本，但要控制主模型版本、研究範圍、資料與工具條件，記明補查預算差異。
- C 對 B 是整體使用方式的比較，混合了模型、介面、原生搜尋與人工互動，不能把差異全歸因於 agent 數量。
- 分別記總歷時、用戶主動操作時間、API 實際用量與工具費。ChatGPT 訂閱使用不能報作「零成本」，取不到逐次成本便標未知／另列訂閱及使用限制。API cached input 等也分開。
- 先看是否交出有根據且一致的投資建議、是否漏掉會改變決策的事，再看速度與成本。格式修正次數與重大分析錯誤分開記。

刪掉「只有同時更快、更便宜且沒有更多錯漏才成立」。較高成本若換來重要新證據，仍可能值得；一宗案例也不足以決定六角色在所有股票上無效。這次是操作試用，足以決定下一輪怎樣做。

## 七、v1.1 的交付次序與六問答案

建議順序：

1. 共用資料／計算函式接薄服務；研究可以補查網頁及報告、讀舊研究、保存並出既有股票頁。對齊本次儲存規則所需的最小發布調整。
2. 接上最小 API 覆核入口，部署並驗證 ChatGPT 工具連接。這一步須在 C 的覆核之前，不放在三組比較之後。
3. 用 INTU 跑 C，立即交完整頁面及本次最痛的缺口。收錄評級、當日價值情境、期限目標的依據或缺口、關鍵價位及條件計劃。
4. 視實際成本跑 B 作比較；需要時才補 A。依用戶使用情況加局部更新、產業依賴與觀察名單；不等待框架選型才提供介面。

| 原提案六問 | 直接回答 |
|---|---|
| 1. 接受服務端 API 覆核嗎？ | 接受；API 優先是部署選擇，CLI 並非必須無限制運行。 |
| 2. 儲存原則足夠嗎？ | 方向足夠，合併矛盾條文並保存實際決策數字及口徑；不新增供應商每日續存。變化只能承諾相對上次研究或供應商可取的歷史。 |
| 3. 四張表夠嗎，依賴誰標？ | 可起步，需有假設到公司／層／版本的映射及時間觸發。模型說明依賴，程式建索引；不單從引用猜邏輯。 |
| 4. C 如何公平計費計時？ | 分列歷時、人工操作、API／工具費及訂閱使用；只比較觀測得到的成本，不把未知當零，不當純架構實驗。 |
| 5. 第二股選誰？ | INTU；TTD 備選。選擇基於問題涵蓋度，不基於私人持倉，也不先下投資結論。 |
| 6. 工具缺什麼？ | 財務資料、搜尋／事件、報告與摘錄入庫、TA、舊研究讀取、覆核任務及發布。可共用底層函式，不逐工具另造框架。 |
