對我們而言，最重要的是分清三種「對」：

| 要確認甚麼 | 我們模型中的例子 | 適合的方法 |
|---|---|---|
| 資料與理解正確 | 財報數字是否抄對？管理層說的是目標還是已實現結果？ | 原始來源查核、口徑與日期檢查、語義審閱 |
| 計算與推導遵守規則 | 是否讀取舊結果？必要條件是否被當成充分條件？ | 一般程式檢查；部分規則可用 Lean 證明 |
| 判斷具有預測力 | 能否辨認未來 2–4 季會持續改善的公司？ | 凍結預測、機械基準比較、到期結果與前瞻測試 |

Lean 的正式保證主要落在第二行：對精確表達的定義、前提及命題，檢查證明是否成立。它不會自動驗證前提是否描述真實世界。[Lean 官方介紹](https://lean-lang.org/theorem_proving_in_lean4/Introduction/)

例如，我們可能讀到：

> 毛利率改善、訂單回升，因此未來幾季的改善較可能延續。

這是一項需要實證支持的預測判斷。如果為了讓 Lean 接受，先加入「毛利率改善且訂單回升，必然導致改善延續」這個假設，後面的證明即使通過，也沒有回答我們真正想知道的問題。

**最容易出錯的接點，是把研究文字翻譯成形式命題的那一步。** 「支持某個假說」可能被翻成「假說成立」；「尚未找到證據」可能被翻成「假說不成立」。Lean 可以嚴格檢查翻譯後的命題，但仍需要我們審核它有沒有忠實保留原意。官方文件也明確區分命題、假設與證明。[命題與證明](https://lean-lang.org/theorem_proving_in_lean4/Propositions-and-Proofs/)

因此，我會在我們的共同研究流程中，按以下次序引入。

1. **先讓每項重要判斷可以追查。**  
   為核心結論記錄：明確命題、觀察期限、來源及當時可取得日期、事實／管理層說法／模型推斷的身份、依賴的假設、反證條件和版本。研究正文仍然可以用 Markdown，不需要整份改寫成 Lean。

2. **把固定規則做成獨立於 LLM 的檢查。**  
   例如：引用是否存在；輸入更改後，下游結果是否重算或標記過期；尚未到期的案例是否被錯當失敗；資料缺漏是否被默認為零或否定；評估時是否偷偷換了結果定義。這些是我認為目前應優先投入的部分。

3. **再挑一小塊用 Lean，證明它對所有符合前提的輸入都成立。**  
   可選的是已穩定、反覆使用、錯了會影響很多結果的規則。例如依賴狀態的傳遞，或未來若有情景權重轉移，其非負性與總量守恆。一般測試檢查具體案例；形式證明可以在明列前提下覆蓋整類輸入，這才是額外價值。[Lean 官方介紹](https://lean-lang.org/theorem_proving_in_lean4/Introduction/)

其中，我尤其想保留 **「未知」這個狀態**。投資研究經常遇到資料不足、證據互相衝突或結果尚未成熟。這些不能被壓成單純的真／假。證明沒有完成，也不等於命題已被推翻。

如果做 Lean 試點，我會要求它回答一個具體問題：**相對於普通程式檢查，它額外防止了哪一類錯誤，是否值得維護第二套規格？** 同時需要確認實際執行的程式符合被證明的規格；只證明旁邊一份抽象模型，保障範圍仍然有限。驗收也不能只看「編譯成功」——Lean 允許用 `sorry` 暫留證明缺口，會發出警告，所以完成標準必須排除這類未完成證明及未審核的假設。[Lean 官方文件](https://lean-lang.org/theorem_proving_in_lean4/Interacting-with-Lean/)

**對這輪 84 宗，我會繼續原定評估，不會等全面導入 Lean 才跑。** 可以加入上述資料、版本和流程檢查，但檢查失敗的案例仍須留下紀錄，修正或明列無法評估的原因，不能藉此悄悄收緊候選池。

我會把近期工作順序定為：先確認研究流程可重播、結果可追查，再用完整案例比較 LLM 與機械基準；當中反覆出現、且能精確定義的規則錯誤，就是最值得交給 Lean 的第一批工作。

| 一個行業假設 → 多家公司結論 | 共用前提改變後，所有依賴它的分析都需要覆核 | 先做依賴與版本檢查，再考慮證明狀態傳遞規則 |

這些直接對應①過去的問題。早期版本曾有「重大損害＝不買」的接法；後來改成情境表，正是為了分開**條件成立時的損害、條件有多可信，以及現價是否充分反映損害**。filecitefile_00000000cd3882099a54c6e2bc64127f filecitefile_00000000dad8820e9ca4bc3dad19e12f

但這裏有一個很值得用①理解的限制：**有些問題，Lean 會證明它算得完全正確，卻仍然沒有投資上的解釋力。**

例如報告提到，曾用衝擊日價格反推估值倍數，再用這個倍數判斷現價。簡化成每股收入 \(S>0\)、現價 \(P\)：

\[
M=\frac{P}{S},\qquad V=M\times S=P
\]

Lean 可以證明這個恆等式。可是它沒有提供獨立的公平價值依據；報告中的價格判詞也仍然呈現接近零或反向的分辨力。filecitefile_00000000da7081f689a1706eae3eb85f

所以，①真正需要一起做好的是：

- **經濟規格審核：**我們究竟在計算甚麼？這個結果能回答哪個問題？
- **形式驗證：**給定這份規格，推導和計算是否確實成立？

這符合 Lean 的保證範圍：驗證精確表達的命題是否由指定前提推出；前提與規格是否適合描述現實，仍要另外判斷。[Lean 官方介紹](https://lean-lang.org/theorem_proving_in_lean4/Introduction/)

而且，「現價要求」本來就可以合法地使用現價。假如我們問的是「在指定利潤率、折現率和期限下，現價要求收入跌多少」，反推是有意義的。需要避免的是把**從現價解出的隱含條件，再當成獨立證據證明現價合理**。這個分界，比全面禁止使用現價更重要。

對①的敘事分析，我還會特別保留一條規則：**沒有找到某個必要條件的證據，只能記作未知；不能直接判定條件不成立。** 否則系統可能因為研究不完整，就把市場恐懼判成錯誤。即使形式化後的推導成立，輸入的「否定」仍可能根本不成立。

我會趁②的 84 宗仍在開發時，給①一個很小、可完成的工作包：

1. **沿用一宗已研究的行業事件，選兩至三家不同傳導機制的公司。**

2. **先用既有錯誤做重播。**

3. **只挑一段真正穩定的規則寫 Lean。**  
   例如一組公司損害上下界的計算，或共同前提失效後哪些正式結論不再具備所需條件。驗收要看它額外攔住了甚麼錯誤，以及實際研究程式是否確實使用那套規格。

**這值得做，但不能憑「Lean 通過」就恢復①的獨立排序、排除或交易權限。** 它可以提高研究推導的可信程度；①能否判出錯價、能否帶來選擇優勢，仍是另一道考試。

### ASSISTANT

**Lean 是一種程式語言，同時是一套定理證明工具（proof assistant）。它本身不是 agent 架構，也不是 LLM 治理模型。** 你可以把它接進自己的架構，讓它負責某些形式證明的檢查。[Lean 官方介紹](https://lean-lang.org/theorem_proving_in_lean4/Introduction/)

**對你描述的系統——主要靠非結構化資料、contextual agent judgment，另加少量 TA——我目前不認為 Lean 是關鍵依賴。** 它可能在局部增加價值，但研究品質的主要瓶頸仍是證據理解、經濟機制判斷，以及這些判斷能否經得起結果驗證。

我也需要修正前兩則的表達：我把「形式化研究規格」與「採用 Lean」講得太接近了。你很需要前者；後者則需要另外證明值得投入。

Lean 實際做的事情，可以這樣理解：

1. 人或 LLM 把問題寫成精確的定義、假設與命題。
2. 人或 LLM 提供形式證明，也可使用 Lean 的自動化工具協助。
3. Lean 的核心檢查器核對這份證明，是否真的支持那個命題。

**負責最後檢查的是程式規則，不是另一個 LLM 對答案是否合理的評價。** 但它檢查的是提交給它的形式命題，並不會自動閱讀整份研究報告、理解商業背景，再判斷分析是否可信。[Lean 的形式證明與類型系統](https://lean-lang.org/doc/reference/latest/The-Type-System/)

例如，你的 agent 可能提出：

> 客戶轉換成本高、續約仍然穩定，因此這次 AI 替代恐懼可能被市場高估。

這裏有幾個不同的研究責任：

- 「轉換成本高」是否有可靠證據，還是管理層自己的說法？
- 續約數字是否滯後，尚未反映新的替代壓力？
- AI 是否會改變原本的轉換成本？
- 即使恐懼被高估，現价是否已經反映這一點？

**Lean 不會自行解答這些問題。** 如果 agent 直接把「高轉換成本會阻止 AI 替代」寫成假設，Lean 可以檢查後面的推導，但最值得懷疑的那一步已經被放進前提了。

這就是你系統與數學證明的重要差別：你主要做的是**根據不完整證據，提出解釋、比較情境、更新對未來的判斷**，也就是歸納與溯因推理。Lean 的主要強項，是對已明確形式化的演繹推導提供保證。它也能處理機率模型的數學性質，但不會因此證明那些機率符合現實。

所以，如果你問「它是不是一種治理 LLM 分析的方式」，我的回答是：**它可以成為治理流程中的一個驗證工具；整套治理仍然要由我們設計。**

| 你需要治理的事情 | 主要方法 | Lean 的位置 |
|---|---|---|
| 引用是否真實、是否支持結論 | 原文核對、來源與日期追蹤、語義審閱 | 無法自行保證 |
| agent 是否忽略背景、反證或替代解釋 | 結構化研究要求、針對性反方審閱、案例評估 | 作用有限 |
| 假設是否被悄悄寫成事實 | 明列陳述身份、依賴關係及不確定性 | 可約束正式表示，但翻譯仍要審核 |
| 指標、估值計算與固定規則是否正確 | 一般程式、資料檢查、測試 | 少數複雜且穩定的規則值得形式證明 |
| 判斷是否有預測力與增量價值 | 凍結預測、基準比較、到期評分與校準 | 無法代替實證 |

對你而言，我會優先建立一個很薄的**可追查判斷格式**，讓 agent 在保持自由分析的同時，為每個重要結論交代：

- **結論：**究竟在主張甚麼，期限是多久。
- **證據：**哪些原始材料支持它，哪些與它矛盾。
- **推斷：**從證據走到結論，依賴哪些尚未證實的假設。
- **失效條件：**看到甚麼就必須重新評估。
- **依賴與版本：**上游資料或假設改變時，哪些下游結論需要覆核。

這會令我們的共同研究流程更清楚：

| 要回答的問題 | Agent 的工作 |
|---|---|
| **發生了甚麼，為何可能延續？** | 從非結構化資料找出機制、適用條件、反證及時間限制 |
| **市場目前反映了甚麼？** | 結合現價、估值、預期變化、價格與可觀察的資金行為；分開觀察與推測 |
| **現在參與是否值得？** | 比較情境、可能回報、損失、期限與成本，說明判斷對哪些假設敏感 |
| **我們錯了會怎樣？** | 定義失效證據、覆核或退出條件，以及多筆持倉是否共用同一風險 |
| **這套判斷真的增加了價值嗎？** | 與簡單基準比較，追蹤漏選、誤選、成本、回撤及事前判斷的校準 |

經濟模型和金融模型在這裏很有用：它們能迫使 agent 解釋**「如果我們相信這個故事，價格、數量、成本與現金流應該怎樣變」**，也能找出不一致之處。但模型給出的仍是帶條件的結果；機率可以用區間和敏感度表達，不必為了完整而填入虛假的精確數字。

同樣，R&R 不能只由目標價與止蝕價決定。兩者提供的是計劃中的盈虧比例；是否值得下注，還取決於各結果的可能性、實現時間，以及實際損失可能偏離計劃多少。風控能限制承擔的風險，卻不會自動創造正的預期回報。

至於「贏過 90% 的玩家」，我會保留為抱負，但評估時用可測量的標準：**扣除成本後，相對合理基準是否有增量回報，而承擔的回撤、集中度與尾部風險是否值得。** 我們不需要先證明比九成人聰明；需要證明這套額外研究，比更簡單的做法帶來更好的結果。

R&R 應按實際方案計算。以單一目標的多頭交易為例：

\[
\text{回報／風險倍數}
=
\frac{\text{目標價}-\text{入場價}}
{\text{入場價}-\text{止損價}}
\]

純算術示例：入場 100、止損 94、目標 118，毛回報／風險為 **3 倍，即風險：回報＝1：3**。

若價格已升至 108，而止損和目標的依據仍然成立，比率就變成：

\[
\frac{118-108}{108-94}\approx0.71

我也因此修正前面「Markdown 加輕量索引便可先做」的建議：介面可以簡單，但你現在明確要求跨股票、產業、價值鏈的增量更新，資料層就需要結構化。這已經有實際功能上的理由。

你需要的機制可以概括為：

> **發現資料變更 → 判斷改了什麼 → 找出受影響的分析 → 更新相關判斷 → 呈現對投資計劃的影響。**

**首先，系統要分別保存「來源」、「事實與假設」、「分析結果」的版本。**

| 層面 | 保存什麼 | 為什麼需要獨立版本 |
|---|---|---|
| 原始來源 | 年報、逐字稿、新聞、產業報告、資料商回傳 | 同一網址可能修訂，財務資料也可能重述 |
| 事實與主張 | 收入、指引、產能預測、供應鏈關係、分析師觀點 | 一份文件包含多個不同影響範圍的內容 |
| 分析狀態 | 公司基本面、產業展望、瓶頸、估值假設、技術判讀 | 各維度有不同更新頻率 |
| 投資計劃 | 目前建議、入場條件、目標、風險回報、等待事項 | 需要知道建議如何隨資料和價格改變 |

**每份分析還要記錄：它使用了哪些來源和上游分析的哪些版本。**

例如，某份投資計劃可能使用「公司基本面 v4、產業展望 v7、估值 v3、今天的技術分析」。今天價格更新，可以沿用仍適用的前三項，再更新技術面和計劃。

這種根據輸入版本和依賴關係重用成果的做法，在資料工程已有成熟概念；Dagster 的文件也描述了相同的版本與快取原理。我們可以採用這個設計原則，工具選擇另行決定。[版本與快取機制](https://docs.dagster.io/guides/build/assets/asset-versioning-and-caching)

**來源分類和分析維度，也應該是兩個獨立方向。**

一份產業報告可能同時涉及：

- 幾家不同公司；
- 一個價值鏈環節；
- 需求、產能、定價、庫存等不同維度；
- 不同的預測期間。

所以不能只把它放進某隻股票的資料夾。**文件保存一份，相關主張連到多個公司、產業環節和論點。**

例如：

```mermaid
flowchart TD
    R["新產業報告"] --> I["更新產能與定價假設"]
    I --> A["公司 A 毛利情境"]
    I --> B["公司 B 擴產論點"]
    A --> V["公司 A 估值"]
    B --> W["公司 B 觀察條件"]
    V --> P["公司 A 投資計劃"]
    Q["公司 A 價量更新"] --> T["技術結構與動能"]
    T --> P
    P --> D["工作台變更摘要"]
    W --> D
```

這裡應該**共用產業層研究，再分析各公司的不同曝險**。同一項供給增加，對買方、供應商、設備商可能有不同意義，不能把產業結論原封不動套到全部股票。

來源之間有分歧時也要並存，保留各自的依據；最新一篇報告不應自動覆蓋其他觀點。

**每日更新應按影響範圍分流。**

| 發生的變化 | 通常需要更新的內容 |
|---|---|
| 一般價量變化 | TA、動能、估值折讓／溢價、入場條件、R&R |
| 業績及指引發布 | 財務、基本面、經營預測、估值、投資論點及計劃 |
| 產業需求／供給新資料 | 共享產業假設，以及受影響公司的相關情境 |
| 利率、匯率等變化 | 依賴這些因素的預測、折現率和估值 |
| 你的持倉或風險預算改變 | 部位建議、集中度和投資計劃 |
| 催化劑到期、假設超過覆核期限 | 即使沒有新文件，也要重新檢查等待條件 |

因此，「今天只有价格變動」通常可以只更新價格相關部分，前提是其他必要資料已正常檢查，而且原有假設仍在適用期內。

還有一個重要例外：**異常價格行為可以觸發補查。** 如果股價突然大幅偏離預期，即使現有新聞來源沒有回傳新消息，也值得檢查公告、同業、產業或其他來源，不能直接推論「基本面一定沒變」。

**時間至少需要分開記錄四件事。**

- **公開時間：**市場何時可以知道這項資訊。
- **取得時間：**系統何時實際拿到它。
- **適用期間：**它說的是哪一季、哪一年，或哪段預測期間。
- **最後檢查時間與結果：**何時成功檢查過來源。

「今天成功檢查，沒有新增消息」與「今天抓取失敗」必須是不同狀態。重新下載一份舊報告，也不能把它變成今天的新資訊。

前端則可以簡潔地呈現有用的事實，例如「新聞已檢查至今日收市；基本面沿用最新季報」，避免用一個籠統的「今日更新」掩蓋不同維度的資料時間。

**Diff 也需要分層，不能只比文字。**

我會採用這個次序：

1. **內容有沒有變？** 用來源 ID、內容指紋等方式辨識重複資料和修訂，排除廣告、排版等噪音。
2. **實質內容改了什麼？** 比較財務欄位、指引、論點及相關段落，保留原文位置。
3. **對既有判斷有沒有影響？** 找出依賴這些內容的假設與分析，決定重新計算或交給模型覆核。

新業績不是只與上一份文件作文字比較；它還要與上年同期、上一季、原先指引及我們的預測比較。這些比較對象也應明確保存。

Agent 更新時應收到：

> **原有論點和關鍵假設＋新增資料及差異＋相關原文上下文＋本次需要重評的問題。**

這能減少重讀，也避免只看幾行 diff 而失去上下文。重大事件、長時間未覆核或出現矛盾時，再安排較完整的回讀，防止錯誤摘要被一代代沿用。

**以這些已確定的需求，我現在會建議從第一版使用 PostgreSQL 管理版本與依賴。**

具體分工可以保持簡單：

- **原始文件及轉換後 Markdown：**保存於檔案／物件儲存。
- **PostgreSQL：**管理實體、來源版本、事實、關係、分析版本、依賴及更新任務。
- **價格與財務數值：**按時間序列與財務期間儲存；分析記錄所引用的資料版本。
- **Markdown／生成頁面：**作為閱讀和報告輸出。

產業和價值鏈需要圖狀關係，但初期可以用 PostgreSQL 的關係表表示。它也支援遞迴查詢，用來追蹤直接和間接關係；是否需要 GraphDB，之後按實際查詢複雜度決定。[PostgreSQL 遞迴查詢](https://www.postgresql.org/docs/current/queries-with.html)

資料版本之外，分析也應記錄模型、提示詞和估值程式的版本。方法改變時，系統才知道哪些既有結果值得重新處理。

**你最後每天看到的，應該是這種變更摘要：**

> **本次更新：價量與交易計劃**  
> 基本面及產業假設沿用。價格進入原定阻力區，動能減弱，現價入場的 R&R 下降；建議改為等待回踩確認。

或者：

> **本次更新：產業供給假設**  
> 新報告改變了擴產時程的判斷。系統已重新評估三家相關公司的曝險，其中兩家的盈利情境與投資計劃需要調整。

第一版的驗收就應包含這兩種行為：**價格更新能局部重算；產業更新能找到相關股票並傳遞影響。** 這會直接決定你往後每天使用系統的成本、速度和可信程度。

### ASSISTANT

**兩者確實正在變得相似。我優先選 WeKnora，是因為我們目前最需要補齊的是「外部資料變成可持續使用的研究知識」這條流程。Agent Memory 的優勢則較集中在「讓不同 agent 接續彼此的工作」。**

但這是有條件的選擇，我上一則把「先接 WeKnora」說得太確定了。

**騰訊為什麼做兩套？公開定位能解釋部分原因，內部產品策略則沒有足夠資料確認。**

從官方文件看，兩者的出發點是：

| | WeKnora | TencentDB Agent Memory |
|---|---|---|
| 首要問題 | 大量文件如何被理解、搜尋及持續整理？ | Agent 做過的工作，如何被下一次工作重用？ |
| 主要輸入 | 外部文件、網頁、知識庫 | 對話、任務經驗，以及文件和程式碼 |
| 主要資產 | 文件、檢索片段、來源引用、Wiki | Chat Memory、Skills、Wiki、Code-Graph |
| 產品重心 | 知識的取得、整理、閱讀與使用 | 記憶的提煉、共享及分配給 agent |

這是依據兩者的[官方定位](https://github.com/Tencent/WeKnora)與[Agent Memory 說明](https://github.com/TencentCloud/TencentDB-Agent-Memory)作出的整理。

我的推斷是：**它們由不同問題切入，擴充功能時逐漸走到同一區域。** 文件平台加入 agent 和長期記憶；記憶平台加入文件、搜尋和 Wiki，重疊自然增加。

所以，今天已不能用「一個是 RAG，一個是記憶」把它們完全分開，也沒有理由假定我們必須兩套一起使用。

**為什麼目前仍偏向 WeKnora？主要是三個實際原因。**

**第一，我們每天新增的主要內容是外部市場證據。**

年報、逐字稿、產業報告和新聞，會不斷進入系統。我們需要保留它們、找出相關段落、比較來源、整理公司與產業知識，並讓強模型隨時回讀原文。

WeKnora 已提供多格式文件處理、混合檢索、來源閱讀和文件管理介面。這段現成流程，直接對應我們要建的產品。[WeKnora 功能說明](https://github.com/Tencent/WeKnora)

Agent Memory 也能處理文件；我目前看到的差異，是 **WeKnora 對整個文件使用流程提供較完整的現成介面和功能**。這不代表它的金融文件解析準確度已經勝過另一套，這部分尚未實跑比較。

**第二，你要求能直接閱讀、檢查和比較研究結果。**

你不只需要 agent「記得某個產業看法」，還需要能點開：

- 這個看法根據哪些文件？
- 哪一段支持它？
- 最新版本改了什麼？
- 公司頁和產業頁如何連起來？

WeKnora 的來源引用、Wiki 瀏覽、修訂歷史和差異比較，能直接成為工作台的研究閱讀部分。[Wiki 功能與版本機制](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/14-wiki.md)

**第三，我們可以把它當成獨立的知識服務，保留自己的投資分析流程。**

強模型照樣負責市場、價值鏈、基本面、估值、TA 和綜合判斷；需要證據時呼叫 WeKnora。投資論點、依賴關係、持倉和計劃仍由我們的應用管理。

這樣採用它的理由很具體：省下文件處理與研究閱讀的開發工作。

**不過，有一種情況，我會改選 Agent Memory。**

如果你現有資料管線已經把文件可靠地轉換、索引、保留來源，而且也有足夠好用的閱讀與搜尋方式，當前主要問題是：

> 換一個 session，agent 就忘記之前的分析；不同 agent 重複研究；研究結論和方法無法接續。

那 Agent Memory 就更接近真正的缺口。它本來就把跨 agent 的記憶共享、skills 和知識分配作為核心，也有跳過未變更來源的增量 Wiki 處理。[Agent Memory 定位](https://github.com/TencentCloud/TencentDB-Agent-Memory)、[增量處理程式](https://github.com/TencentCloud/TencentDB-Agent-Memory/blob/feat/server_team/MemoryKnowledge/src/engines/wiki/index-db.ts)

**而你最關注的「產業更新後，哪些股票、估值和計劃需要重評」，兩套都仍需要我們補上投資領域的依賴邏輯。** 單靠這項要求，尚不能分出誰更適合。

因此，目前我的選擇依據是：

- **文件處理、來源閱讀、研究 Wiki 尚待建立：優先 WeKnora。**
- **上述能力已有，主要缺跨 agent 的工作接續：優先 Agent Memory。**

以我們目前討論的完整工作台來看，我仍偏向 **WeKnora 作為知識層候選**。但「資料來源已接通」究竟已經做到多少文件處理、索引和閱讀功能，會直接影響這個選擇。如果那部分其實已經齊備，再加入 WeKnora 就可能造成重複建設。
