# 投研工作台 v1 提案——計劃、檔案架構與資料源(供外部評論,2026-09-14)

> 依據:D-179(用戶定義產品)、D-177(根基重整)、D-178(②考試 84 宗為回歸集)、② 對帳單 §十二 第 17–21 條(用戶與 GPT 五輪對話的採納項)。本檔答三件事:**計劃怎樣拆、檔案怎樣擺、資料從哪裡來**。已核實與未核實分開標;「實測」指本日在本機直接呼叫過。

## 零、一頁摘要

- **形態**:三層——證據層(檔案,內容定址,只准追加)、研究卡層(Markdown 加結構化卡頭,git 為歷史)、索引與狀態層(SQLite;可重建的索引與必須持久保存的執行狀態分開)。
- **核心物件**:論點(thesis)。公司卡內多個論點各有編號;產業卡按價值鏈環節;市場卡按主題。每個論點記證據依賴與更新訂閱兩種關係。
- **更新**:新資料入庫 → 標記涉及的公司、主題、鏈位 → 配對訂閱 → 只重評受影響的層 → 程式重算計劃與風險回報 → 每日變更摘要。
- **計劃**:D12 升格為新 Epic「投研工作台 v1」,六件交付品、約十八張票;第一個可用里程碑是股票頁(三至五隻起步名單);第二是觀察名單與每日差異;第三是今日市場。
- **資料**:TradingKey 不接;yFinance 降為歷史底稿;DefeatBeta、富途 MCP、Longbridge MCP 三個接口全部已通,Longbridge 實測有 2019 年起的「公布時共識對實際」與 2021 年起的月度評級目標價歷史,富途網頁那七頁不用抓。

## 一、目標與邊界

用戶定義(D-179 原話節錄):「leverage the best capability of the latest front-tier LLM model with the highest intelligence, with the latest information … forcing the discipline to provide the best investment advise … a complete analysis of not only from K Chart, but Market, Value-Chain, Fundamentals, then TA. And taking the correct timeframe which match with the investment principle of myself and the knowledge from the masters.」

三個入口:股票分析、觀察名單與持倉追蹤、今日市場。六層分析紀律:市場與宏觀 → 產業與價值鏈 → 公司基本面 → 估值與預期 → 技術與市場行為 → 投資綜合。股票頁首屏六行:目前建議、主要理由、關鍵假設、最強反證、改變行動的條件、與上次相比。

第一版不做:PostgreSQL、LangGraph、Neo4j、React 應用與伺服器、WeKnora / Agent Memory、多寫入程序、港股與 A 股(資料接口有,但六層紀律先在美股跑通)。

## 三、檔案架構

### 3.1 目錄樹

```
Karst/
  strategy/            正本:framework、principles、candidates、投資委託、資料來源、地圖、specs/
  cards/               研究卡層(Markdown,入 git)
    companies/<CIK>.md         公司卡:多個論點,各有編號
    industries/<chain>.md      產業卡:按價值鏈環節;假設帶編號與版本
    market/<topic>.md          市場卡:利率、流動性、需求、政策等按主題
    plans/<CIK>-<date>.md      已發布投資計劃(每次一份,不改寫)
  evidence/            證據層(不入 git;只准追加;內容定址)
    sec/               既有 data/sec(申報索引、財務事實、年報全文;8-K 快取待建)
    prices/            既有 data/prices(日線;續抓)
    transcripts/       DefeatBeta 逐字稿快照
    broker/            富途、Longbridge 回傳的 JSON 快照(每次呼叫一份,帶取得時間)
    docs/              你放進來的檔案:PDF、HTML、文字(見 3.9)
    manifest.jsonl     每份證據一行:編號、來源、公開時間、取得時間、適用期間、內容指紋、路徑
  state/               索引與狀態層(SQLite)
    index.sqlite       可重建:實體、來源版本、主張與假設、卡版本、依賴、訂閱
    state.sqlite       必須保存並備份:任務、重試、來源游標、最後檢查、發布日誌
  publish/             發布日誌(只准追加,入 git):每次發布一行——卡版本、輸入版本、證據編號
  karst/               程式:入庫、路由、發布、估值、技術、頁面
  inbox/               你丟資料的地方(見 3.9)
  site/                生成頁面(每股一頁、名單頁、今日頁;可發布為 Claude 頁面或本機開)
  research/            回歸集與外評紀錄(既有)
  library/             圖書館(既有)
```

**公司卡卡頭**(結構化,程式生成與驗證):

```yaml

chain_positions: [chain:gaas-substrate:upstream, chain:inp-substrate:upstream]

  - id: T1  horizon: 2-4Q  status: supported|challenged|insufficient

    evidence: [ev:edgar:3f9a…, ev:defeatbeta:tx:…, ev:lb:consensus:…]
    subscriptions: [company:0001051627:8-K, company:0001051627:transcript, chain:gaas-substrate:*]
    next_check: {event: Q3 業績, expected: 2026-10-30}
    invalidate_if: [...]
layers:
  L1: {version: 3, inputs: [...]}   L2: {...}  L3: {...}  L4: {...}  L5: {...}  L6: {...}
plan: plans/0001051627-2026-09-13.md
```

**卡身**:首屏六行;六層各一節(每節末尾列「本節所用證據」與「本節假設」);變更紀錄(每版一行:改了什麼、因為哪份證據)。

**產業卡**:鏈位、成員(公司與角色:買方、供應商、設備商、替代品)、假設清單(每條帶編號、版本、支持與反對證據、覆核日期)、共同情境。**市場卡**:主題、目前判讀、依賴它的產業與公司數。

### 3.4 索引與狀態

`index.sqlite`(可由卡頭、證據清單、發布日誌重建):entities、evidence、claims(主張與假設,含版本)、card_versions、dependencies(卡版本 × 層 × 證據或假設版本)、subscriptions(卡 × 層 × 事件型態)。

`state.sqlite`(不可重建,須備份):tasks(待重評的卡與層、原因、狀態、重試)、cursors(每個來源最後成功檢查的時間與位置)、publish_log(與 `publish/` 同內容,方便查詢)。

GPT 第一點的回應:「六張表可重建」改為上面的分法;歷史依賴由 `publish/` 日誌重建,不走 git 歷史。

### 3.5 兩種關係

- **證據依賴**:這版卡的哪一層用了哪份證據、哪個假設版本。用來答「這個判斷憑什麼」與「證據被修訂時誰要重看」。
- **更新訂閱**:這張卡的哪一層要在什麼事件發生時重評。用來答「新業績來了誰要動」。新文件從未被引用也能觸發,因為入庫時先標記涉及的公司、主題、鏈位,再與訂閱配對。標記由程式(申報索引、代號對照、鏈位成員表)加便宜模型(產業報告、新聞的實體與主題抽取)完成;新關聯(例如報告揭示未登記的供應關係)以「待確認關係」入索引,由產業層判斷確認。

### 3.6 發布協定

1. 模型只輸出結構化修改提案(哪一層、哪幾格、新內容、所用證據編號、所依賴假設版本、基於哪個卡版本)。
2. 程式驗證:編號存在、證據在索引、基於的卡版本仍是最新(否則標過期,重整合或重跑)。
3. 三步發布:寫結果與輸入版本到 `publish/` → 生成 Markdown 並提交 git → 更新索引與任務狀態。任何一步中斷,重啟時按 `publish/` 對帳補完。單一發布程序;分析可並行。

### 3.7 更新路由與時間觸發

按受影響範圍,不寫死層數。常見路徑:價格變動 → L5、L6 加估值折讓與反向估值隱含要求(程式重算)、組合曝險;業績或指引 → L3 起;產業資料 → L2 起並經成員表傳到公司;宏觀 → 依賴該主題的 L1 與 L4 折現率;持倉或風險預算改變 → L6 與計劃。無新文件亦觸發:催化劑到期、等待事件未發生、假設到覆核日;異常價格變動觸發補查(不推論基本面沒變)。

### 3.8 產業與價值鏈網絡

第一版用關係表表示,不用圖資料庫:`chain_positions`(鏈、位置、描述)、`memberships`(公司 × 鏈位 × 角色 × 生效期 × 依據證據)、`assumptions`(鏈位 × 假設 × 版本)。種子是 V1 期人手鏈位表(65 條鏈、347 行,tag `pre-reset-2026-09-13` 內),由 W6-1 還原並按今日口徑清理。「產業更新 → 逐家重評」那一步用 ① 的暴露差異判斷能力卡(同一事件對不同公司的經濟暴露)。遞迴查詢(某環節受阻影響誰)SQLite 支援;真要多層路徑探索頻繁才評圖資料庫。

### 3.9 你怎樣提供新資料

三種方式,全部落到同一條入庫流程:

| 方式 | 做法 | 入庫時系統做什麼 |
|---|---|---|
| **放檔案** | 把 PDF、HTML、文字、截圖放進 `inbox/`,檔名隨意;可選附一行 `note.md` 講來源與日期 | 解析成文字(PDF 抽字;掃描件走 OCR,標「OCR」)、算內容指紋、記取得時間、**問你或推斷公開時間與適用期間**(推斷的標「推斷」)、標記涉及公司、主題、鏈位、移入 `evidence/docs/`、配對訂閱、生任務 |
| **貼連結** | 在 `inbox/links.md` 每行一條網址,可加註 | 抓取存快照(不是只存網址)、其餘同上;抓不到即報「未取得」,不會靜默略過 |
| **指定來源訂閱** | 在 `strategy/資料來源.md` 的訂閱表加一行:來源、查詢(例如富途新聞搜尋某關鍵詞、Longbridge 某公司申報)、頻率 | 程式按頻率拉取,記游標與最後檢查;「今天檢查過沒有新東西」與「抓取失敗」分開記 |

每份文件存一次,主張連到多家公司與環節;不同來源有分歧時並存。

## 五、驗收

W1 三項(見表);W3:起步名單每隻一頁,換股不改流程;W4:價格日局部重算、產業更新傳到相關股票;整體:任何已發布計劃可取回所用研究與證據版本;每個交付品報模型費用與每股耗時。

## 六、風險與不做

- 模型寫壞卡頭:寫入時驗結構,壞的不落地;索引重建即全面核對。
- 券商接口失效或改版:證據層存每次回傳快照,分析不直接依賴即時呼叫;失效時卡標「該來源未更新」。
- 記憶污染:現時分析不受影響;回歸集與時間留出測試另計。
- 不做:PostgreSQL(單機單寫入者)、LangGraph、Neo4j、WeKnora(跨文件查找開始漏或慢時再評)、React 應用。
