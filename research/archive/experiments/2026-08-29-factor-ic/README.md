## 跑法

```
set PYTHONUTF8=1
python -m karst.gateway factor ingest-alpha158 --snapshot 2026-08-28-493fd1df1cb9
python -m karst.gateway verify
python experiments/2026-08-29-factor-ic/run_factor_ic.py --store karst.sqlite
```

第一句把標普 500 快照(625 個實體)的 Alpha158 入檔,約 4–5 分鐘;第三句對兩個
宇宙 × 三個窗口逐條因子算 IC/ICIR,約 25 分鐘(起步十二隻很快,標普 500 那部分
佔了幾乎全部用時——158 條因子 × 625 個實體 × 約 2,900 個交易日,一個窗口約
7 分鐘)。

## 對齊與 IC/ICIR 怎樣算

做法住在 `karst/factorpredict.py`(本票新寫,唯一入口新增 `karst factor ic` 子命令
可查一條或幾條因子的即時結果)。三件事要記住:

1. **回報起點是可執行時點那根 K 線的開價,不是知情當日的收價**——一個因子值
   最早可以拿來做的那一刻。
2. **持有期怎樣量**:第 1 個交易日(可執行時點那根)開價買入,持有到第 N 個
   交易日(含首日在內)的收價賣出。`horizon=1` 即當日開至當日收,`horizon=5`
   約一個交易周,`horizon=21` 約一個月。
3. **逐日 IC 按知情時點那一日分組**(橫向比較當日全部實體的因子值排名與各自
   其後 N 日回報排名),用 Spearman 等級相關;ICIR = 滾動窗口內 IC 的均值除以
   標準差。

## 一句業務結語

**在標普 500(625 隻大盤股)上,158 條 Alpha158 因子,三個持有期窗口(1、5、21
個交易日)加起來,沒有一條因子的預測力達到「有訊號」的門檻(\|IC 均值\| ≥
0.02)——量價類技術因子在這個宇宙目前測不出可用的單因子訊號,持有期拉長到
一個月表現略好但仍然不夠。** 相反,在起步宇宙那十二隻(較集中的組合),同一批
因子(尤其是波幅與極值類)在持有一個月的口徑下有明顯訊號,84 組因子 × 窗口
組合達標。這個對比支持研究票結語的判斷:**不能假設 Alpha158 這批量價因子直接
搬去大盤股廣譜宇宙就有用,要合併多因子、或者縮窄到有基本面篩選的子集才有機會
浮出訊號**——現在有 Karst 自己的數據撐住這句話,不再只是引用別人的覆現。

## 未解

- 158 條因子逐條 × 兩個宇宙 × 三個窗口共 948 組,只挑了「\|IC 均值\| 排名」與
  「達標條數」兩個角度摘要;完整逐條數字在 `summary.json`,日後要看某條具體
  因子(例如挑選策略引用哪幾條)可以直接查那個檔或用 `karst factor ic`。
- Alpha158 入庫途中一次因記憶體不足半途死掉(見下面「附註」),已改
  `karst/gateway/alpha158.py` 分批寫入修好;因為半途死掉那次已經把全部 158
  條因子推上第 2 版(procedure 指向標普 500 快照),十二隻宇宙那批值仍在
  各自第 1 版——`run_factor_ic.py` 現在按「這一版的 procedure.input_data_version
  是不是這個快照」去揀對的版本,不用「最新版」硬猜,但這代表庫內同一條 Alpha158
  因子名字現在有兩個版本並存(v1 綁十二隻快照、v2 綁標普 500 快照),日後若要
  在同一個畫面同時列兩個宇宙的因子,要留意這一點,不能假設「一個因子名 = 一個
  版本」。

## 附註:入庫途中一次記憶體不足(已修好,不是本票的核心結論)

第一次入庫標普 500 快照的 Alpha158 時,`karst/gateway/alpha158.py` 原本的做法
是 158 條因子的值一次過拼成一張表才寫檔——標普 500 這個量級(625 實體 × 約
2,929 交易日)拼出來要 2 億 7 千萬列,單一條時間戳陣列就要 6 GB,觸發
`numpy._core._exceptions._ArrayMemoryError`,半途死掉。已改為按目標列數分批
拼、分批寫(`_TARGET_ROWS_PER_CHUNK`,本次跑出來標普 500 分成 16 個檔),十二隻
那種小宇宙因為一批就能裝下全部 158 條,批次名與行為與 KARST-064/068 那時一字
不差(`tests/test_alpha158_ingest.py` 全數通過)。`karst.factorstore.FactorValueStore.read_long`
本來就支援「一個因子版本的值分散在幾個批次檔」,讀取介面不必改。
