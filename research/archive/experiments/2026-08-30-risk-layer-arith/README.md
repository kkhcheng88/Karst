# KARST-089:共用風控層的注碼算術是否寫了兩次

日期:2026-08-30 · 只查證,沒有改 `karst/` 任何一個檔 · 定義庫唯讀開啟

源自 `research/2026-08-30-architecture-review-backend.md` 候選八(D-043):
架構審視懷疑 `karst/engine/vectorbt_engine.py` 有兩處各自算共用風控層的部位/比重,
即同一條數寫了兩次。本檔是逐項對照的結果。

## 結論一句

**乙:兩處是刻意分開的,各有理由,不應合併。** 在一切行得到的輸入之下,兩處算出來
的股數逐位(bit-for-bit)相同;唯一算得出不同結果的那一格,要成交價細到 5e-324
(浮點次正規數)才踩得到,真實股價不可能去到那裡。而且沒有任何一個已登記的運行
用過乙處那條路,所以**沒有一個盤數受影響**。

## 兩處在哪

行號按 2026-08-30 當日的 `karst/engine/vectorbt_engine.py`;`compare.py` 會把該
幾行原文抄入 `result.json`,好等下一個人核對行號有沒有飄。

| | 甲處 | 乙處 |
|---|---|---|
| 位置 | 第 207–219 行 | 第 319–328 行 |
| 所在 | `_order_rules_nb`(njit 內圈) | `VectorbtSignalMatrixEngine.simulate_rules` |
| 走哪條引擎路 | `from_order_func`(正路) | `from_signals`(**對照臂**) |
| 形態 | 純量,逐根 K 線逐隻股票算一次 | numpy 向量,整張矩陣一次過算 |
| 引擎名 | `vectorbt-order-func` | `vectorbt-signals` |

乙處是**對照臂**:本檔開頭的說明與 `VectorbtSignalMatrixEngine` 的說明都寫明,
它存在的目的是用另一條引擎路重算一次,證明兩條路在同一個基數、無熔斷之下算得出
同一個數——即是說,兩處算式**貼到逐個運算符一樣是刻意的**,源碼第 323 行那句註解
「與 `_order_rules_nb` 逐個運算符對齊,好令兩條路算出同一個浮點數」正是這個意思。

## 逐項對照

### 輸入

| 項目 | 甲處 | 乙處 | 同否 |
|---|---|---|---|
| 成交價 | `open_[i, col]` | `fill = panel.open.to_numpy()` | 同一份開價表 |
| 止蝕價 | `stop_level[i, col]` | `signals.stop_level` | 同一份 |
| 單筆風險上限 | `risk_per_trade` | `params.sizing.risk_per_trade` | 同一格參數 |
| 單一持倉市值上限 | `max_position_fraction` | `params.sizing.max_position_fraction` | 同一格參數 |
| 注碼基數 | `c.value_now`(當下權益);`fixed_equity_basis > 0` 時改用固定基數 | 一定是 `params.initial_cash`(起始本金) | **語意不同,刻意** |

注碼基數那一格是兩處**唯一一個真正的分別**,而且是明文設計:`RiskFractionSizing`
的說明寫明當下權益是「唯一正確的一個」,起始本金「已知會令回測系統性偏樂觀,
只保留給對照臂重現訊號矩陣路徑那條走樣的路」。乙處看不見組合的現金與權益
(`SignalContext` 沒有這兩格),所以它做不到當下權益;它的處理不是靜靜當作起始
本金,而是**當場拒收**(第 313–317 行拋 `RuleNotExpressible`)——寧可拒答,
不會默默算個假數出來。

### 公式

| 步驟 | 甲處 | 乙處 | 同否 |
|---|---|---|---|
| 止蝕距離 | `price - stop_level[i, col]` | `fill - signals.stop_level` | 逐個運算符相同 |
| 股數 | `risk_per_trade * equity / stop_distance` | `risk_per_trade * equity / stop_distance` | 逐個運算符相同 |
| 上限股數 | `max_position_fraction * equity / price` | `max_position_fraction * equity / fill` | 逐個運算符相同 |
| 封頂 | `if shares > cap: shares = cap` | `np.minimum(shares, cap)` | 有限數之下相同 |

運算次序兩處一樣(先乘後除、左至右),兩處都行 IEEE 754 雙精度,所以有限數之下
兩處**逐位相同**,不只是「數值接近」。

### 四捨五入

**兩處都沒有取整,一個四捨五入都沒有。** 股數容許小數,由頭到尾以浮點數交出去;
兩處在這一格完全一致,沒有一邊偷偷取整、另一邊不取。

### 邊界處理

| 邊界 | 甲處 | 乙處 | 同否 |
|---|---|---|---|
| 止蝕距離為零 | `not (stop_distance > 0)` → 不落單 | `stop_distance > 0` 不成立 → 不落單 | 同 |
| 止蝕距離為負(止蝕高於成交價) | 不落單 | 不落單 | 同 |
| 成交價缺值(NaN) | 止蝕距離變 NaN → 不落單 | 同 | 同 |
| 止蝕價缺值(NaN) | 同上 → 不落單 | 同 | 同 |
| 股數 ≤ 0 | `not (shares > 0)` → 不落單 | `shares > 0` 不成立 → 不落單 | 同 |
| 超出單一持倉市值上限 | 封頂至 `cap` | 封頂至 `cap` | 同 |
| 恰好等於上限 | 不改(`>` 不成立) | `minimum` 取同一個數 | 同 |
| 起始本金 ≤ 0 | 會退回當下權益 | 會照用 | 型別層封死:`RuleStrategyParams` 驗起始本金必為正數,踩不到 |
| **成交價為浮點次正規數** | 股數與上限同為 `+inf`,`inf > inf` 不成立 → **落一張無限大的單** | `isfinite(shares)` 不成立 → 不落單 | **不同** |

最後那一格是兩處**唯一算得出不同結果**的輸入:乙處多一道 `np.isfinite` 閘,甲處
沒有。要踩到它,成交價要細到 5e-324(雙精度的最細次正規數),同一時間止蝕價要令
止蝕距離同樣細到溢出——真實股價與已調整價都不可能去到這個數量級。

## 對照腳本與結果

- 腳本:`compare.py`
- 結果:`result.json`

腳本不是把兩段算術抄一份出來重寫(抄的話,證到的只是我抄得準),而是**原地行真碼**:

- 甲處:用 numba 的 `.py_func` 取回 `_order_rules_nb` 未編譯的原函式,配一個假的
  逐格情境物件直接呼叫,行的是源碼那一段。
- 乙處:把 `vbt.Portfolio.from_signals` 暫時換成一個攔截器,接住 `simulate_rules`
  算好交出來的 `size` 矩陣即中止——所以第 319–328 行那段算術真的行了一次。

定義庫用 `sqlite3` 的 `mode=ro` 唯讀模式開,只行 `SELECT`。**刻意不行
`DefinitionStore.open()`**:那條路會建表兼寫 `schema_meta`,即是會寫庫。參數集
經 `DefinitionStore` 的查詢介面(`list_param_sets` / `get_param_set`)讀回,
再經 `karst.strategies.trend_swing.read_setup` 還原成引擎收得到的參數。

### 跑出來的數

| | |
|---|---|
| 對照過的參數集 | 12 個(庫內全部帶注碼參數的參數集) |
| 對照格數 | 216 格(12 個參數集 × 18 個輸入) |
| 逐位相同 | 204 格 |
| 不同 | 12 格 —— 全部是同一個輸入:次正規成交價那一格 |
| 可以原封不動走乙處的參數集 | **0 個** |

最後一行要留意:庫內 12 個參數集**沒有一個**跑得動乙處,因為每一個都同時踩正
乙處明文拒收的兩件事——熔斷開住(`risk.monthly_loss_cap = 0.06`),以及注碼基數
取當下權益(`sizing.equity_basis = current_equity`)。要令兩處都行得到來做對照,
腳本要先把參數改成「關熔斷、基數改起始本金」;這一步本身就是結論的一部分。

另外,12 個參數集雖然是 12 份,但注碼那幾格取值完全一樣(單筆風險 0.02、
持倉上限 0.25、起始本金 1,000,000),分別只在入場回望日數;所以注碼算術上
它們其實只有**一種**組合。

### 一個要講清楚的限制

這 12 個參數集全部叫「示例-KARST-028」,即示例參數集,按 D-038 未經用戶對齊、
不算現役。庫內目前**沒有**用戶對齊過的規則類參數集——這不是本票查證不足,是庫
現時就只有這些。取值一改,上面的結論不用重跑也成立:兩處算式逐個運算符相同,
與取值無關。

## 對盤數有沒有影響

**沒有。** 庫內全部運行的引擎分佈:

| 引擎 | 正式運行 | 掃描運行 |
|---|---|---|
| `vectorbt`(目標比重路,不經這兩段算術) | 3 | 8,305 |
| `vectorbt-order-func`(甲處) | 9 | 0 |
| `vectorbt-signals`(乙處) | **0** | **0** |

乙處那條路**一個運行都未曾產出過**。即是說,就算兩處真的分歧,亦分歧不到任何一個
已登記的數字上。所以本票不是丙,不需要寫 `.kira/assumptions.jsonl`。

## 建議(不在本票做)

判定是乙,所以不合併。兩處合不合得埋,技術上也是「不」:甲處是 njit 內圈的純量
碼,乙處是整張矩陣的 numpy 碼,兩者的形態不同;而且乙處作為對照臂,靠的正是它
自己行一次,合併之後那個對照就自我印證,證不到嘢。

按票的要求列出應加註解的位置:

1. **`_order_rules_nb` 第 212–219 行之上** —— 加一句指去對照臂:這段算術在
   `VectorbtSignalMatrixEngine.simulate_rules` 有一份刻意對齊的孿生碼,改這裡就要
   同步改那裡。現時只有乙處那邊寫了「與 `_order_rules_nb` 逐個運算符對齊」,甲處
   這邊沒有回指,所以由甲處入手的人看不見還有第二處。
2. **`_order_rules_nb` 第 216–219 行(封頂那兩句)** —— 註明乙處多一道
   `isfinite` 閘,甲處靠 `stop_distance > 0` 與 `shares > 0` 兜底;兩者在真實價位
   之下等價,只在次正規成交價那個踩不到的角落分歧。

兩項都是加註解,不改行為。要不要做,由開不開實作票決定,本票不動。
